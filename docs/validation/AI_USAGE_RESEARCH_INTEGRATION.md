**Legend**

## 0. Two real, separate data subsystems (read this before the table)

The research assumed one usage-analytics substrate. Quotalis actually has **two independent, non-overlapping real data subsystems**, and conflating them is the single biggest fabrication risk in adopting any of this research:

1. **Quota/spend history** (`rust/src/dashboard_data.rs`, backed by `rust/src/history.rs`'s `usage_samples` table). Every provider writes into this: `used_percent`, `remaining_percent`, `resets_at`, `window_id`/`window_key`/`window_minutes`/`window_label`, `account_scope` (`observed`/`unresolved`/`legacy`), `captured_at`, and optionally `cost_used`/`cost_currency_code`/`cost_measurement_kind`/`monetary_quantity_kind`. **This schema has no columns for tokens, request counts, or model identity** — `DataAvailability::from_samples` (`dashboard_data.rs:206-218`) hard-codes `has_token_data: false`, `has_request_data: false`, `has_model_data: false` with a doc comment explaining exactly this: *"providers only ever report percentage/cost facts through this pipeline... keeping them explicitly false here is what keeps a future Dashboard UI from inventing per-model or per-token analytics this store cannot support."*

2. **Local CLI-log token/model scanner** (`rust/src/cost_scanner.rs`, `rust/src/codex_costs.rs`), Codex and Claude only. This scans local JSONL session logs and produces real `input_tokens`/`output_tokens`/`cached_tokens`, `sessions_count`, `by_model`/`by_model_tokens` (per-model token counts), and `by_speed`/`by_speed_tokens` (Codex tier split) — surfaced to the UI as `ProviderChartData.tokensHistory`/`localUsage` (`apps/desktop-tauri/src/types/bridge.ts:851-891`) and rendered in `ChartsSection.tsx`'s "tokens" tab, scoped per `accountEmail`. **Critically, the dollar cost computed from these tokens (`total_cost_usd`/`by_model`/`by_speed`) is permanently gated off** — `CostSummary::cost_eligible()` (`cost_scanner.rs:194-196`) always returns `false` today because "the billing channel can never be established" (subscription-included vs. per-token-metered API use is indistinguishable from the log format alone — `cost_scanner.rs:11-40`). Token/model/session **counts** remain valid and shown; **dollar figures derived from them are not**.

Any research idea that says "token totals" or "model breakdown" must be checked against which of these two subsystems (or neither) it maps to.

## 2. Summary for the acting session

### Safe to build now (A/B — real data, cite the field)
- Everything already listed under items 1–7, 14–17, 21–28, 32, 34 (provider-level), 36–38: quota %, multi-window, reset countdown, banked-credit history (Codex), multi-account comparison, spend/cost with Spend≠Balance≠Credits enforced, time-series trend charts (usage/spend), timezone-aware ranges, period-over-period comparison, burn-rate/pace/ETA (already shipped, reuse `PaceSnapshot`), freshness/staleness, coverage/"insufficient data" states, the attention/alert feed, KPI/gauge/sparkline/stacked-bar/treemap/sunburst/provider-level-waterfall renderings of the above, a customizable widget grid, and ECharts adoption as a rendering layer.
- Codex/Claude **token counts and per-model token counts** (not dollar cost) from the local-log scanner (`cost_scanner.rs`) are real and account-scoped — safe to visualize as tokens, never as cost.
- Wayfinder gateway route/savings data (item 39) is real but **gateway-scoped, not account-scoped** — label it as such, don't fold it into per-account KPIs.

### Must never be fabricated (D — hard no without new engineering + explicit product decision)
- **No locally-estimated dollar cost from tokens** for any provider — `CostOrigin::LocallyEstimated` exists only as an unused enum variant; the billing-channel ambiguity (subscription vs. API) is proven unresolvable from current log formats (`cost_scanner.rs` doc comment).
- **No per-model/per-tool dollar cost breakdown** — `CostSummary.by_model`/`by_speed` are permanently ineligible for display (`eligible_by_model()` always `None`).
- **No token totals for any provider except Codex and Claude** — the other ~35 provider adapters have no token field anywhere in their pipeline.
- **No reasoning-token tracking** — not a captured field.
- **No MCP/tool/agent call telemetry, latency, or cost attribution** — zero instrumentation exists.
- **No session/project/repo/branch drill-down** — only a bare session *count* exists for Codex/Claude; no per-session record.
- **No model-response latency/TTFT/percentiles** — the only latency-shaped field (`fetchDurationMs`) measures Quotalis's own status-API fetch, not the AI provider's response time; presenting it as model performance would repeat the exact mistake the research itself warns against.
- **No multi-period exhaustion forecasting or anomaly detection** — the codebase already made and documented this decision (`EXHAUSTION_PROJECTION` marked `unsupported`, reason `"workloadNotEstablished"`). Overriding it requires a deliberate, explicit product decision, not an incidental side effect of adopting research ideas.
- **No provider efficiency/quality scoring** — no outcome signal exists to compute it from.
- **No budget enforcement** — this app observes, it does not sit in the traffic path.

### Deferred, needs new instrumentation (C)
- Calendar/hourly heatmap and histogram widgets: the underlying samples already exist (`captured_at`-bucketed), so this is genuinely a "build a widget" task, not a "capture new data" task — lowest-risk C on the list.
- Reset-evidence state machines (observed/inferred history) for providers other than Codex.
- Any Sankey-style flow diagram beyond provider-level spend totals.
